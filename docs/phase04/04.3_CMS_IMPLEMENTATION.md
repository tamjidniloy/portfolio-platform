# Phase 04.3 — CMS, Content Management & Publishing: Engineering Handoff

**Status:** Candidate implementation, pending full acceptance. **Approved product baselines:** SRS-R1, AUTH-R1, DB-R1 (19 tables), API-R1 (37 operations). **Critical dependencies:** executable Phase 04.1 migrations, real 04.2 WebAuthn login/owner provisioning and production security tests remain unfinished.

## Code delivery

- `domain/cms/content-contract.js` defines draft validation, 13 approved content types, published required fields and a deliberate public DTO allowlist. Research scientific status is separate from CMS publication status.
- `server/cms/service.js` implements owner-bound create/read/list, immutable revision save, optimistic locking, private preview, restore as a NEW private revision, atomic publish/unpublish across snapshot/editorial state/redacted audit/outbox, transactional idempotency, slug-change redirect metadata.
- `server/cms/public-reader.js` queries ONLY `published_snapshots`; no joins with private drafts, owner credentials or contacts.
- `server/cms/http.js` exposes only the implemented API-R1 subset, requiring DB-verified active owner sessions, 15-minute idle timeout, exact Origin and per-session CSRF on owner mutations; bounded pagination and no-store.
- React Router private `/admin` workspace and `/admin/content/:id` editor with labeled accessible forms, private revision history, publish/restore/unpublish; no anonymous registration or login is added. Server-side loaders/actions demand verified owner and CSRF.
- Public SSR `/projects`, `/projects/:slug`, `/research`, `/research/:slug`, and `/work` permanent redirect to canonical `/projects`; published-only sitemap from known snapshots when enabled; Writing navigation appears only after an article is published, and secondary collections do not generate nonexistent detail URLs.

## Deployment safety

The runtime deliberately does not auto-create tables, users, passkeys or sessions; disabled by default. CMS routes only mount after explicit opt-in:

```text
CMS_API_ENABLED=true
CMS_DATABASE_URL=<approved PostgreSQL DB-R1 connection / scoped grants>
CMS_PUBLIC_ORIGIN=https://<your real approved hostname>
CMS_CSRF_SECRET=<random server-only secret of at least 32 bytes>
```

**Do not enable** until final DB-R1 reviewed migrations are applied and the 04.2 authenticator ceremony provides real verified owner sessions. The existing 18-table candidate migration is a separate disposable fixture and cannot be used for this DB-R1 CMS.

## Verification

Dedicated `devfolio_cms_ci` disposable native PostgreSQL 16 database. The suite applies approved DB-R1 reference DDL, creates test-only accounts/tokens through an **unexposed trusted test adapter**, and exercises actual SQL transactions, public/private projection, optimistic locking, draft invariants and rollback. No live database or staging was tested. `npm run cms:test:db` is only safe against the explicitly named loopback test DB and rejects production.

**Do not mark 04.3 complete** until the blocking login, release migrations, complete publication UI, private browser E2E, all 37 API contract integration and remaining content/SEO/retention tests pass.

## Enabled-mode end-to-end HTTP/SSR CI check

A second server runs in GitHub Actions against the same **ephemeral CMS test DB**, with a synthetic HTTPS public origin and CI-only CSRF secret. `scripts/cms-smoke.mjs` checks server-rendered published research and detail, public research/site JSON, published-only sitemap and denial of anonymous `/admin` and private mutation. This is a local runner HTTP smoke, **not** a full browser WebAuthn E2E or a managed production test.

## Approval versus implementation

All 76 requirements and the 19-table/37-operation contracts are approved as *target specifications*. This branch implements the Phase 04.3 CMS portion only. A safe default-off feature flag means no real private authoring session exists before the separately required WebAuthn ceremony; it cannot be described as fully operational or ready for production. In the approved deployment, configure a *scoped* DB user and review trusted proxy/HTTPS origin before enabling.
