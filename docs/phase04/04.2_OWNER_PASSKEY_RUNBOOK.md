# Phase 04.2 — Owner Passkey Provisioning and Recovery (R1)

**Contract:** AUTH-R1 approved. Server implementation uses pinned `@simplewebauthn/server@14.0.3`; browser uses pinned `@simplewebauthn/browser@14.0.0`. User verification, origin, RP ID, 5-minute single-use challenge and signature checks are mandatory. Session cookie is HttpOnly/Secure/SameSite=Strict with server DB revocation and 15-minute idle/60-minute absolute expiry.

## Operator provisioning (never web signup)

1. Apply the approved release migrations into a **new empty** DB under a dedicated migration role; verify checksums, backup and grants.
2. Configure `CMS_API_ENABLED=true`, `CMS_DATABASE_URL`, `CMS_PUBLIC_ORIGIN=https://approved-domain`, `CMS_CSRF_SECRET` (high entropy), `WEBAUTHN_RP_ID=approved-domain`, and correct TLS hosting.
3. In a restricted operator terminal, set `OWNER_BOOTSTRAP_DATABASE_URL` to the reviewed DB, `OWNER_BOOTSTRAP_CONFIRM` to its exact database name and `OWNER_BOOTSTRAP_EMAIL` to the actual owner email. Run `npm run auth:bootstrap`; it refuses if an owner already exists.
4. The one-time randomly generated 43-character token is displayed **once** in the operator terminal and hashed at rest; valid for **15 minutes**. Enter in `/admin/setup`, register Windows Hello/passkey through the browser. The authenticating challenge is regenerated with 5-minute expiry. The server validates cryptographic attestation and activates the owner only after success.
5. In `/admin`, register a second independently held passkey, generate 10 one-time offline recovery codes and store them outside the website. No real owner email/token is stored in GitHub.
6. Sign out and test login, wrong origin, expired/replayed challenge, and credential revocation. Do not claim live authentication before this physical authenticator ceremony.

## Recovery policy

If you lose one passkey, use the second. Offline recovery codes are **one use**, 128-bit random; entering one code revokes that code but **does not** create a full CMS session or let a remote attacker register a new passkey. Actual account restoration additionally requires a documented trusted operator identity verification and an out-of-band staged recovery ceremony. No email-only recovery or password bypass is added.

## Operations

- Authentication endpoints: `/api/v1/auth/passkey/options`, `/auth/passkey/verify`, bootstrap options/verify (no public signup), session logout, owner-only credential enrollment/revocation, recovery code rotation and restricted recovery.
- Login is enabled **only if** CMS is intentionally configured on a properly migrated database. Default feature flag is OFF.
- Browser hardware/WebAuthn enrollment and managed staging verification must be performed by the human owner; CI can test runtime denial paths, persistence and negative assertions but cannot create a real biometric/passkey ceremony or sign for the owner.
