# Phase 04.5 — Live Operations Runbooks (candidate until rehearsed)

**Rule for all incidents:** do not expose credentials, private media, DB backups, passkey challenges or contact content in chat, tickets, GitHub, logs or public status pages. Capture UTC timeline, release SHA, command/event IDs, actor, impact, test evidence and next action. Contact owner through a previously verified private channel. Escalate suspected privacy leakage immediately.

## Deployment, startup, rollback (INC-01)
**Trigger:** ALB unhealthy target or `/readyz` returns 503, 5xx alarm, failed SSM job.
1. Compare CloudWatch ALB 5xx + unhealthy targets, EC2 StatusCheckFailed and DB availability. `/healthz` distinguishes app process from DB connectivity.
2. Review only sanitized request logs and `journalctl -u devfolio` / CloudWatch; do not dump runtime.env. Confirm deployed SHA, EC2 health and RDS DNS/TLS.
3. Release workflow fails if health does not recover and `deploy-host.sh` reverts to previously healthy release. Verify `readlink -f /opt/devfolio/current`, health and anonymous admin denial. If migration made prior schema incompatible, **do not** unilaterally restore production DB: apply approved forward-fix or incident restore plan.
4. Record start/end, status, root cause and follow-up. Production rollback drill required before go-live.

## Passkey, session compromise, operator recovery (INC-02)
**Trigger:** abnormal auth denials, account lockout, loss of all authenticators.
1. Disable owner-facing routes through the reviewed feature flag or network access; protect visitor-facing public pages where possible.
2. Use 04.2 operator recovery ONLY after independent owner identity verification and redeemed offline code; recovery revokes all authenticator sessions and requires new owner passkey.
3. Rotate CMS CSRF, provider keys, database credentials through reviewed secret rotation and graceful restart after planning session invalidation.
4. Verify two independently stored passkeys and offline codes after recovery. No email/password fallback, no bypass.

## Database failure, backup and point-in-time restoration (INC-03)
**Trigger:** RDS alarm, corrupt data, accidental destructive change.
1. Stop affected writes and any maintenance timers, preserve incident audit, check RDS health and last restorable timestamp.
2. Run PITR through `ops/aws/restore-drill.sh` only after target/subnet/SG review. It creates a **new isolated DB**; source remains untouched.
3. Connect from SSM-controlled maintenance environment, test checksums, migration ledger, row counts, selected known-safe sample data, restrictive grants and regression smoke. Record selected restore point, latest possible restore timestamp, elapsed time and data loss in UTC.
4. Only after an owner-controlled cutover approval may DNS/connection strings change. Rehearse rollback to source. Isolated restore has cost; delete only with recorded permission. Verify encrypted backup expiration and 30-day PITR.

## Contact and email backlog (INC-04)
**Trigger:** contact accepted (202) but owner notification absent; outbox DLQ nonzero.
1. Verify private contact message in owner inbox and outbox event state; **do not** include sender details in alert.
2. Check timer/service and Resend verified sender/domain; provider outage can result in retry/dead letter; verify idempotency and retry threshold with an authorized disposable test.
3. Avoid re-enqueueing blindly; provider idempotency has bounded windows, so reconcile before retrying after a long outage.
4. Maintain separate monitoring of outbox service failure and dead-letter count. An unmonitored scheduled process does not satisfy acceptance.

## Media, object deletion and CDN (INC-05)
**Trigger:** upload CORS failure, digest mismatch, unexpected object exposure, cache stale after unpublish.
1. Keep `MEDIA_ENABLED=false` while bucket policy/cors and private staging are validated. Never enable public-read ACL.
2. Check allowed MIME/size and presigned conditions, object digest, service grants scoped to `private/staging/*`; do not print storage keys in tickets.
3. Retired assets queue durable deletion; confirm object deletion and orphan sweeps, and document any external provider retention conflict.
4. For Cloudflare optional mode, verify purge job status and actual public cache response; otherwise use default no-store on dynamic requests.

## Security/privacy and retention (INC-06)
**Trigger:** leaked private payload, unusual contact volume, retention request, hold conflict.
1. Disable affected endpoints and preserve only minimal forensic metadata. Notify the authorized privacy incident contact through approved channels.
2. Apply reviewed 90-day contact/365-day audit and legal hold policy; verify the operator-only `retention:plan`, then require exact database confirmation before applying.
3. A DB deletion is not proof that media objects, backups and third-party logs were erased. Track them separately and honor legal obligations.
4. Restore any legitimately withheld data only under formal approval and least privilege.

## Cost and availability escalation (INC-07)
**Trigger:** AWS Budget notice, SNS alert or unexpectedly rising monthly charges.
1. Inspect account spend and cost allocation; budgets are not hard caps.
2. Compare RDS Multi-AZ, ALB hours, traffic egress, storage, snapshots, log volume and SSM charges with the approved budget.
3. Restrict costly nonessential staging activities through an approved change, not unscheduled deletion of data; preserve backups and incident evidence.
4. Reassess provider and monthly cap before raising instance sizes or activating production.

## Readiness record for every rehearsal
Record date, environment, owner/reviewer, exact app commit + artifact SHA, infra plan/apply change ID, region, redacted configuration version, GitHub workflow URL, observed log timestamps, alarm test delivery, tested expected/actual results, RTO/RPO numbers, open risks and **explicit owner signoff**.
