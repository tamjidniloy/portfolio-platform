## Why there are no live migrations

**The candidate DDL is intentionally not copied into production migration directories or applied to user databases.** It remains under Phase 03 documentation as a proposal. A temporary CI-only database called `devfolio_candidate_ci` is created by native PostgreSQL and destroyed with the ephemeral runner. The validation module `server/persistence/candidate-only.js` rejects production mode, remote hosts and databases other than `devfolio_candidate_ci` / `devfolio_candidate_test`. Candidate tests fail closed if that URL is missing. `npm run db:test:candidate` is ONLY for disposable local/CI databases.

The deployed application still has no schema migrations, private read API, owner login or publishing endpoint. The candidate transaction functions are not imported into SSR routes. They are isolated design-validation prototypes, not an authorization implementation.

## Proposed migration system (requires owner ADR)

Use `node-pg-migrate` 9.0.0 after SRS/MFA/DB/API freeze (https://www.npmjs.com/package/node-pg-migrate), keeping SQL transactions visible, migration ordering checked, reviewed immutable files committed and an independent privileged migration DB role. Integrate checksum/provenance verification into CI prior to modifying an approved migration; do not assume the tool alone enforces custom checksum immutability. `pg` remains the production query driver. **No migration tool has been installed yet**, since schema/tool approval is open.

For reviewed future changes: write numbered migrations with one-way safety plan, locked version/fingerprint, transaction and rollback plan, isolated DB integration tests, then staged/approved production execution. Never auto-run schema migrations in the Express request lifecycle or during `npm run dev`. Destructive steps require explicit backup and separate approval. SQL `CREATE DATABASE` is administrative setup outside transactions, not an application migration.

## Candidate security observations for owner review

1. Candidate `admin_users.password_hash`, `auth_challenges.code_digest` and `password_reset_tokens` need MFA/recovery choice before defining final auth persistence. Historical email OTP is not accepted as NIST 800-63B out-of-band MFA.
2. Contact consent fields, retention deadlines, audit retention, revisions, snapshots and media lifetime cannot be frozen before privacy decisions.
3. JSONB content schemas, field caps, media quotas, public routing, email/storage integration, owner permissions and allowed content statuses require synchronized API/DB/SRS signoff.
4. Indexes in the candidate DDL are proposals; measure plans and data sizes before final index selection.
5. Candidate publishes now require matching source-revision public fields and canonical slug, and use an explicitly allowlisted `{slug,title,summary}` DTO. This narrow preview is **not** final real case-study/publication metadata.
6. Candidate revision SHA-256 is verified against submitted bytes; candidate commands accept an actor UUID as a persistence argument, but **do not verify authorization**; they must stay unreferenced from HTTP until Phase 04.2 and object authorization are implemented.
7. The current CI service role owns its disposable database; production runtime and migration roles must be separate/least-privilege after owner/provider decisions.
