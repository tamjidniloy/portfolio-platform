# Approved DB-R1 migrations — operational runbook

**Engineering status:** versioned 19-table schema + checksum ledger implemented. Production/staging migrations are **never** invoked on app startup.

- `db/migrations/0001_release1_schema.sql`: approved 19-table physical schema, outer transaction removed, owned by release migrator.
- `0002_cms_integrity.sql`: indexes. SQL migration files are immutable after application.
- `npm run db:release:plan`: dry-run against a **real non-production** database, check ordered migration IDs and SHA-256 drift.
- `npm run db:release:apply`: **requires** an exact `MIGRATION_APPLY_CONFIRM` matching the database name in `MIGRATION_DATABASE_URL`; untracked nonempty schemas are refused. Prod requires both `NODE_ENV=production` and `ALLOW_PRODUCTION_MIGRATIONS=true` after separate change approval.
- Prefer a distinct privileged deployment/migration DB role. App runtime and public reader roles must not own tables. See `db/roles/grants.sql`.
- Never run against `devfolio_dev` before verifying its actual contents. Apply first on disposable native PostgreSQL 16, then controlled staging with backup, migration and restoration. Rehearse backup with `pg_dump -Fc` and `pg_restore` into an isolated empty DB. Use `pg_dump --no-owner` for role portability after reviewing security.
- Owner Windows 11 setup requires local Postgres service and pgAdmin backup/restore; credentials never in Git or CI artifacts.

**Formal completion depends on actual staging, backup restore, real WebAuthn and functional acceptance, not migration script syntax alone.**
